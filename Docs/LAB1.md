# Лабораторная работа № 1

**Тема:** тестирование в процессе разработки программного обеспечения.  
**Приложение:** арифметический калькулятор с графическим интерфейсом Windows Forms.  
**Дата проверки:** 06.10.2026.

## Краткий конспект

Модульное тестирование проверяет отдельные компоненты в изоляции. В этом проекте таким компонентом служит `Calculator`, который получает два числа и операцию и возвращает результат. Чистая функция не зависит от окна и поэтому проверяется простыми входными и ожидаемыми значениями.

Интеграционное тестирование проверяет взаимодействие компонентов. `CalculatorSession` преобразует текст пользователя в числа, вызывает `Calculator` и преобразует результат или ошибку обратно в текст.

Системное тестирование проверяет приложение через графический интерфейс: выбор операции, ввод чисел, нажатие кнопки, показ результата, ошибки и очистку формы. Проверки запускают настоящую форму и нажимают её кнопки.

## Результаты тестирования

Запуск: `dotnet test SoftwareTesting.sln` или **Тест → Обозреватель тестов** в Visual Studio. Итог: **22 проверки пройдены**, сборка без ошибок. Уровни проверялись в порядке, указанном в задании.

| Уровень | Проверено | Проблемные ситуации и результат |
| --- | --- | --- |
| Модульный | Сложение, вычитание отрицательных чисел, умножение дробей, деление | Деление на ноль вызывает `DivideByZeroException`; неизвестная операция вызывает `ArgumentException`; переполнение вызывает `OverflowException`. Эти случаи не возвращают ложное числовое значение. |
| Интеграционный | Дроби с запятой и точкой, передача значений в модуль вычисления | Пустое или нечисловое поле даёт сообщение «Введите два числа.»; деление на ноль даёт понятное сообщение; переполнение даёт сообщение «Результат слишком велик.». |
| Системный | Расчёт через элементы формы, обработка ошибки, очистка | После деления на ноль старый результат удаляется и показана ошибка; после «Очистить» удаляются поля, результат и ошибка, операция возвращается к `+`. |

## Воспроизводимые ошибки и исправления

Ниже приведены шесть дополнительных сценариев. Сначала для каждого уровня были добавлены тесты, которые **не проходили** на тогдашней версии, затем отдельным коммитом исправлен код. Это учебные сценарии расширенного тестирования; они не выдаются за ошибки, обнаруженные до создания этих проверок.

| Уровень | Сценарий | Ожидалось | До исправления | После исправления |
| --- | --- | --- | --- | --- |
| Модульный | `Calculator.Calculate(3, 4, "*")` | `12` | `ArgumentException` | `12` |
| Модульный | `Calculator.Calculate(12, 4, "/")` | `3` | `ArgumentException` | `3` |
| Интеграционный | `1,234.5 + 1` | `1235,5` | Сообщение «Введите два числа.» | `1235,5` |
| Интеграционный | `1.234,5 + 1` | `1235,5` | Сообщение «Введите два числа.» | `1235,5` |
| Системный | Вычислить `2 + 3`, затем изменить первое число на `10` | Убрать устаревшее `5` | В поле оставалось `5` | Поле результата очищено |
| Системный | Вычислить `2 + 3`, затем изменить операцию на `×` | Убрать устаревшее `5` | В поле оставалось `5` | Поле результата очищено |

Для воспроизведения откройте историю `git log --oneline`. В ней каждый коммит `test(...)` содержит два теста, которые падают на этом коммите, а следующий `fix(...)` их исправляет. Переключитесь на нужный коммит `test(...)` командой `git switch --detach ХЕШ`, выполните `dotnet test SoftwareTesting.sln` и сравните результат с последующим коммитом `fix(...)`. Вернуться к текущей версии можно командой `git switch master`. Перед переключением сохраните свои незакоммиченные изменения.

Для ручной проверки системных ситуаций запустите форму командой `dotnet run --project SoftwareTesting.csproj` на коммите системного теста и повторите действия из таблицы. На текущем `master` старый результат сразу исчезает при изменении поля или операции.

### Дополнительные замечания по раннему прогону

1. При интеграционной проверке `1,5 × 2` результат сначала показывался как `3,0`. Форматирование изменено на `G29`, теперь отображается `3`.
2. Первая системная проверка не нажимала кнопку: тест создавал форму, но не показывал её, поэтому `PerformClick()` не выполнял действие. Проверка исправлена вызовом `Show()` перед нажатием. Это была ошибка тестового сценария, не приложения.

Системные проверки выполнялись программно на Windows. Визуальная оценка читаемости при разных масштабах экрана и работа мышью человеком в этот прогон не входили.

## Ответы на контрольные вопросы

1. **Приёмы тестирования во время разработки:** сначала модульное тестирование отдельных функций, затем интеграционное тестирование связей между ними, после этого системное тестирование приложения в целом.
2. **Смысл модульного тестирования:** изолированно проверить, что каждая часть программы выдаёт ожидаемый результат для обычных, граничных и ошибочных входных данных.
3. **Особенности интеграционного тестирования:** проверяются интерфейсы и обмен данными уже проверенных модулей; в данном случае — преобразование строк, вызов вычисления и передача результата или ошибки.
4. **Черты системного тестирования:** проверяется готовое приложение с точки зрения пользователя, включая интерфейс и последовательность действий, без опоры на внутреннее устройство вычислительных функций.
